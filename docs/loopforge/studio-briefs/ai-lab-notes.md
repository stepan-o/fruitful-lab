# Loopforge AI lab
## Architecture recommendation for owner review · 22 November 2026

Use one owner-directed workflow for writing, design, art, engineering and browser review. Keep the studio clients independent of the game’s inference service. Use Bob’s post-shift decision as the first local AI experiment and the first reusable portfolio case.

**Owner direction.** Native Codex with the ChatGPT subscription is the primary studio environment. Alibaba Cloud Model Studio is the first alternative provider. The desired Alibaba Coding Plan is unconfirmed. Pi belongs in the lab as an additional client for future controlled workflow comparisons. Langfuse monitors approved experiments and studio assignments on demand. The owner opens specialist threads and controls new providers, purchases, publication and playable acceptance.

**Budget and evidence.** Use local inference for routine game tests. Real web traffic will use a distinct, capped service at up to C$25 per month including its fixed costs. The earlier C$10 one-time planning ceiling applied to the DeepSeek comparison. It stays parked while Alibaba comes first. Alibaba usage, Meshy credits and any later hosted game endpoint each need an identified billing route. No provider account, entitlement, benchmark, integration or spend was established in this review.

### Full system overview

[Explore the interactive studio, game and monitoring views](/stepanoskin/loopforge/design/studio/ai-lab).

The upper paths cover studio production. An owner commission selects a specialist, client and billing route. Text, specifications, design files, software and media reach the same review record through different forms of verification. The lower path covers the running game: only ENGINE admits simulation inputs. Langfuse receives observation data from each relevant path. The lab can stop its dashboard while the game or tests continue.

A fresh chat resumes from those files. Historical chat import is unverified and optional. Paid services and owner-facing review are explicit steps.

**Workflow optimization.** Compare first-pass acceptance, owner correction minutes, elapsed time to a reviewable result and cost per accepted artifact. ### Monitoring and local operation

Each record links the assignment, role, client/harness, provider, billing route, versioned input, artifact/build ID, outcome, measurable usage, time and human verdict. Link a Meshy task ID to its resulting asset and a browser journey to its build. Keep binaries, editable media and test recordings in their appropriate artifact stores; Langfuse can carry a pointer and review score. Verify each client's observable events. Subscription-native chats, provider-side token accounting and third-party UI tools can expose different fields. Use a job-level record when a detailed trace is unavailable. ### The first game experiment

| Controlled condition | H2 | H1 |
|---|---|---|
| What Bob heard | Sam said somebody found a card. | Bob also heard that the loose card was at Ed’s desk. |
| Authored comparison | Ask Ben, the remembered rear witness. | Ask Ed about the loose card. |
| Fact unavailable to Bob | The loose card’s owner. | The loose card’s owner. |

Use three conditions per scene: **rules plus authored line**, **rules plus proposed dialogue** with recipient fixed, and **proposed recipient plus authored line**. A generated line is a study variant for WRITER review. Test delivery and behavior independently. Keep the approved line, slot timing, custody and production outcome available to the baseline. A fourth combined condition is justified only after the two independent results.

**Inference boundary.** SYSTEMS defines legal intentions, evidence and reconsideration triggers. A decision window can open when new evidence arrives, a goal is blocked or an intention concludes. Ordinary motion, perception, resource reservation, custody, action execution and tick ordering remain deterministic. A response proposes a permitted action/listener or a line for an already accepted speaker/listener. Include the actor, opportunity ID, evidence references, run/branch, originating tick/version and expiry. Claim-bearing dialogue proposals refer to attributable evidence. An evidence ID alone cannot certify that free text says what that evidence supports. Arbitrary live prose requires separate validation and WRITER/owner review of its observed error rate. Approved line selection is the fallback.

**Admission and replay.** ENGINE validates scope, current beliefs, actor availability, resource ownership, timing and prior commitment in Rust. Reject duplicate, superseded, stale, cancelled or late results. Deduplicate retries; invalidate old proposals when a run is rewound or branched. Journal the accepted proposal or fallback at its ordered simulation tick, with provenance. Link exact display text to the accepted event. Replay makes zero inference requests. Both presentations consume the same projection. An external client receives only the character’s permitted facts. [Rust BDI](https://github.com/stepan-o/fruitful-lab/blob/7bd5ec8d7493975d4628f4f0f29646c77cbaf314/apps/lab/engine/src/bdi.rs) · [Session and replay](https://github.com/stepan-o/fruitful-lab/blob/7bd5ec8d7493975d4628f4f0f29646c77cbaf314/apps/lab/engine/src/session.rs)

### What earns a playable trial

| Question | Measurement or proposed acceptance condition |
|---|---|
| Can we trust the evaluator? | Hand it a known-wrong output: H2 Bob identifies Ed’s desk or either Bob asserts ownership. The fixture must catch it. Include a valid paraphrase so the grader cannot win by rejecting everything. |
| Does inference improve behavior or dialogue? | For H2/H1, require the expected legal recipient and attributable evidence. Include samples with the lead absent, someone unavailable and two actors competing for the same slot. Score script fidelity, factual grounding, voice and repetition separately. WRITER and the owner review shuffled samples without provider labels. Promote only the component with a repeatable advantage on held-out scenes and an owner-accepted playable result. |
| Does it preserve play and replay? | Forced timeout, missing service, exhausted budget, duplicate delivery, rewind and changed preconditions must yield one legal outcome per window. Compare native and Wasm projections from the admitted record, plus the exact displayed line. Zero replay inference calls and zero clock stalls are proposed gates. |
| Does the Legion have headroom? | On the actual Fedora 45 Legion Pro 5i, verify the RTX 4070 Laptop GPU’s total/free VRAM, driver compatibility, free RAM and SSD, power mode and sustained thermals. The supplied i9-14900HX, 32 GB RAM and 1 TB-class SSD are planning inputs. Record exact weights, quantization, context, concurrency and runtime once chosen. Measure cold start, time to first usable proposal, completed-response p50/p95 and missed decision windows with the editor, game and browser open. Report sample count and frame-time impact. Repeat during a build and with Langfuse running. |
| Is the experience legible? | Observe a fresh player through both versions without explaining Sam’s interrupted line. Afterwards ask what made Bob choose Ben or Ed. Use this alongside the blinded review; record each participant’s explanation and the sample size. Tynan Sylvester, *Designing Games*, ch. 11, “Over-the-Shoulder Playtesting,” printed p. 297 / PDF page 305 (one-based). |
| Can it operate within its budget? | Track request counts, worst-case capped output, paid retries, peak concurrency, fallback rate and cost per completed shift. Prove the hard-stop path under concurrent requests before public use. High task scores alone cannot offset missed scene timing. |

### Execution and costs

**Development target.** Start with one local inference endpoint behind the evaluation runner. llama.cpp is a candidate runtime. Verify hardware before selecting any specific weights. Local and hosted inference should share a small typed request/response contract and fixtures; each deployment requires its own quality and latency measurements. The player's browser needs no model download. Keep the authored rules fallback available whenever a served response cannot be used.

**Public target.** Prefer an on-demand inference provider behind a small app-owned backend adapter; evaluate the existing FastAPI service first. Compare a provisioned server only if traffic supports its fixed cost. Real web traffic uses the service independent of the Legion’s uptime. Assign bounded event types, request sizes and completion limits. Atomically reserve worst-case cost before dispatch, including in-flight calls, then reconcile actual billable usage. A still-unresolved or ambiguous provider charge keeps its reservation. Count retries against the same budget. Apply a conservative CAD conversion, taxes/fees and fixed-cost allowance. Stop dispatching before an additional call could breach the cap. If an upstream route cannot be bounded, keep that route disabled until it can. Live telemetry records operational fields only; maintain counters when the local dashboard is offline.

### Smallest useful implementation after approval

1. AI ARCHITECT, SYSTEMS and WRITER identify the two H2/H1 fixtures, approved lines and one deliberately false claim. ENGINE checks receipt semantics. Implement a local, offline evaluator with a stub response and the rules baseline. The first deliverable is a report where the valid cases pass and the bad response fails for the correct reason.
2. Measure the Legion, select one locally runnable and appropriately licensed candidate, and replay those fixtures against it. Collect detailed local records; review the comparison in on-demand Langfuse. The owner decides whether dialogue, BDI, both or neither progress.
3. Prepare the first Alibaba specialist assignment and a Pi comparison protocol. Once the exact route is confirmed, run an allowed interactive assignment from the same source commit and compare results. Add one art job and one browser test to monitoring when an already-authorized commission needs them. For the portfolio, identify what the owner designed, implemented or reviewed, a failing case and the measured decision.
4. If the result earns a playable trial, ENGINE adds the smallest admission path on the Rust line. Public traffic needs a further owner-approved service, verified cost stop and commercial review. After review, update the public AI ARCHITECT brief and design handoff with the source revision, publishable measurements, owner verdict and remaining limits.

**Open at review:** actual Legion resources, eligible model revision, verified client telemetry, available public hosting overhead, live provider, warm/cold latency, reach of the H2/H1 fixture on the target Rust build, and the owner’s playable verdict. The on-demand dashboard and service are proposals. No install, model download, API call or public deployment was made for this plan.
